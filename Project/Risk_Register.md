|Risk ID|Risk Description|Possible Cause|Probability|Impact|Mitigation/Response Strategy|
|-|-|-|-|-|-|
|R1|Unauthorized access to sensitive information|Improper enforcement of user roles or lack of authentication.|Medium|High|Implement strict user roles in the backend. Ensure that sensitive data (passwords, vehicle IDs, names, phone numbers, etc.) are encrypted (if feasible).|
|R2|Ambiguous requirements|Miscommunication regarding the exact workflow of how parking violations are issued or appealed|Medium|High|Develop user personas early and include detailed use cases. Schedule meetings/interviews so the team and stakeholders can visualize the project before heavy development begins|
|R3|Failure to integrate external APIs|Poor API documentation, rate limits, or lack of team experience|Medium|High|Create mocks of the API functionality at the start. Once frontend development begins, use the mocks in case APIs become unavailable.|
|R4|Team member unavailable|Illness, conflicting exam schedules, or other unexpected personal emergencies|Medium|Medium|Use GitHub and Git for version control, so all members stay updated on the project status. Agree to regular code reviews so all team members stay up to date if someone is missing.|
|R5|No access to a real parking office, leading to guesswork|Inability to establish contact with campus security or parking administration to validate assumptions|Medium|Medium|Attempt early contact with stakeholders. If contact fails, use publicly available campus parking regulations and appeal procedures/information as a foundation.|
